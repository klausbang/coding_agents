Agile V Agent Team

A reusable team of AI agents that plans, specifies, builds, verifies, validates and releases cloud-hosted Python Flask web applications with a database. Each agent is tied to one level of the V-model. A human approves the work at four gates.

The V-model and its agents

The left leg of the V turns needs into precise specifications. The bottom is where code is written. The right leg tests the result. Each test level on the right checks the specification at the same height on the left: level 1 is checked by level 1, level 2 by level 2, and so on. The orchestrator runs the whole V for every sprint.

What each agent does

Each agent is a file .claude/agents/<name>.md, or .github/agents/<name>.agent.md for Copilot, with a fixed role, the files it reads, the folders it may write to, and a Definition of Done. Agents never talk to each other directly. They read and write the shared project/ folder and report back to the orchestrator.

Control

The main session. The only agent that talks to the human.

orchestrator

all levelsOpus

Runs the v-sprint from start to finish. Plans the work, sends tasks to the agents and asks the human for decisions.

  • Turns a sprint goal into sprint-N.md and a short task brief for each agent
  • Starts agents in parallel when their work does not depend on each other
  • Collects the questions agents report, groups them and asks the human at gates G1–G4
  • Updates hitl/status.md after every step. Stops a fix loop after 3 tries and asks the human.

Answers "what exactly do we build?" before any code is written.

Turns the product vision into testable user stories.

  • Writes acceptance criteria as Given/When/Then with IDs (AC-014.2)
  • Captures NFRs: response time, availability, GDPR/privacy, WCAG accessibility
  • Reports anything ambiguous as a question with options to choose from

L2L3Opus

Designs the system's components and the API contracts every other agent builds against.

  • Component model: blueprints, service layer, external integrations (email, OIDC, payment)
  • Writes the OpenAPI 3.1 contract before the endpoints are coded
  • Cloud topology: container service, managed Postgres, key vault, CDN
  • Records each significant decision as an ADR. Sets the NFR budgets, e.g. p95 latency.

stories, NFRs, existing ADRs

database-engineer

L3buildSonnet

Owns the data model and the only path for changing it: migrations.

  • Maintains the ERD and keeps the schema normalized
  • Writes the SQLAlchemy 2 models and Alembic migrations, each with an upgrade and a downgrade
  • Checks migrations for table locks and data loss. Designs indexes and spots N+1 queries.
  • Provides seed data and test fixtures (factory-boy)

app/models, migrations/, architecture/data

security-engineer

L2R2Sonnet

Brings security in at design time and tests it again before release.

  • Writes a STRIDE threat model for each feature, and the authorization rules
  • Checks the code against the OWASP Top 10: access control, injection, CSRF, sessions
  • Runs bandit, pip-audit and gitleaks in CI, and an OWASP ZAP baseline scan on staging
  • Reviews security headers, cookie flags and how secrets are handled
Writes
tests/security, architecture/security
Done
no open high or critical findings, unless the human accepts the risk at a gate

Writes the code test-first, against the approved contract.

  • Uses mocks for dependencies that have not been built yet

code-reviewer

buildread-only

A second pair of eyes on every change. It never edits code.

  • Checks each change for correctness, edge cases and error handling
  • Checks the layering: blueprint → service → model, with no SQL in views
  • Flags security smells, duplicated code and unclear names
  • Reports findings by severity, and the developers fix them

project/sprints/reviews
Done

Right leg: verify & validate

Verification asks "did we build it right?". Validation asks "did we build the right thing?".

verification-engineer

R4R3R2Sonnet

Tests the system at unit, integration and system level, independently of the developers.

  • Derives test cases (TC-xxx) from the acceptance criteria, never from the code
  • Integration tests: Flask test client against a real Postgres (testcontainers)
  • Contract tests with schemathesis against openapi.yaml
  • E2E tests with Playwright and load tests with locust against the NFR budgets. Audits unit test quality.
Writes
tests/integration, tests/contract, tests/system
Done
every TC is linked to an AC and passes, and each failure is filed as a BUG-xxx

validation-engineer

R1Opus

Acts as the user: checks that the product actually solves the problem.

  • Writes Gherkin acceptance scenarios from the AC before any code is written
  • Runs them with pytest-bdd + Playwright on the staging environment
  • Walks through persona journeys to find usability and missing-need gaps
  • Sends new insights back to the requirements-engineer as backlog changes
Writes
tests/acceptance, validation report
Done
every AC has a passing scenario, and the report is ready for G3

How the agents interact

The orchestrator works like a dispatcher. Agents hand work to each other through files in project/, never by calling each other. Hooks and CI enforce the rules, so they do not depend on agents following their prompts. For example, a developer cannot edit an acceptance test.

One v-sprint, end to end

Example sprint goal: "Password reset by email". Every product goes through the same sequence. Only the backlog changes.

Where the human decides

The orchestrator only interrupts the human at these points. Every question comes with options to choose from and a recommendation, and every answer is logged in project/hitl/decisions.md.

G1

Scope

Approve the sprint's stories, acceptance criteria and NFRs.

G2

Design

Approve the API contract changes, DB migrations, ADRs and threat model.

Ask

Clarify

Answer a blocking question at any time. Non-blocking questions wait for the next gate.

G3

V&V review

Accept the test results and the validation findings, or send them back to the backlog.

G4

Release

Approve the production deploy. GitHub's prod environment also requires manual approval.
